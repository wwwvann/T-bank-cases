# Кейс 1 — «Виртуальный Бро»

## Контекст

Учебный продуктовый кейс, выполненный в рамках отбора в Т-Банк.

Задача заключалась в разработке концепции AI-функции для банковского приложения, которая помогает пользователю замечать потенциально рискованные финансовые операции и принимать более взвешенные решения.

## Концепция

«Виртуальный Бро» — AI-помощник, работающий внутри финансового приложения.

Он анализирует финансовое поведение пользователя: операции, переводы, накопления и инвестиции, а при обнаружении потенциально рискованной ситуации предупреждает пользователя.

При этом функция не должна постоянно вмешиваться в обычные финансовые операции. Для стандартных покупок, переводов и платежей помощник остаётся незаметным и активируется только при обнаружении потенциального риска.

### Пользовательский сценарий

1. Пользователь совершает или инициирует финансовую операцию.
2. AI анализирует операцию в контексте предыдущего поведения пользователя.
3. При отсутствии подозрительных признаков операция проходит без дополнительных действий.
4. При обнаружении потенциального риска пользователь получает предупреждение.
5. Пользователь может открыть подробное объяснение и изучить причины предупреждения.

Таким образом, функция должна не блокировать пользователя, а помогать ему принять решение.

## Пример

Пользователь переводит 25 000 ₽ со сберегательного счёта на брокерский и собирается инвестировать всю сумму в недавно появившийся актив.

Для пользователя это необычная операция: ранее он не совершал подобных инвестиций, при этом до конца месяца остаётся мало денег.

AI анализирует дополнительные признаки актива и обнаруживает потенциальные риски.

В момент покупки пользователь получает предупреждение с объяснением причин риска и возможностью подробнее изучить ситуацию.

## Необходимые данные

Для работы функции могут использоваться:

* история финансовых операций за предыдущие 12–16 месяцев;
* профиль накоплений и инвестиций пользователя;
* информация о подозрительных счетах и организациях;
* данные о получателе перевода;
* информация о финансовом рынке;
* контекст операции;
* географические и технические признаки.

Использование каждого источника данных должно быть обосновано его вкладом в оценку конкретного риска.

## Метрики

В первоначальном решении в качестве основной оценки эффективности я предложил сравнивать:

* количество успешных мошеннических переводов;
* общий объём финансовых потерь пользователей по рискованным операциям.

Сравнение предполагается проводить до и после внедрения функции.

Дополнительно эффективность можно оценивать через:

* долю пользователей, которые после предупреждения изменили действие;
* количество подтверждённых рискованных операций;
* долю ложных предупреждений;
* влияние предупреждений на пользовательский опыт.

## Проверка гипотезы

Если другая команда предлагает альтернативное решение той же задачи, сравнивать концепции только на основании экспертного мнения нецелесообразно.

Оптимальный вариант — провести эксперимент:

* одна группа пользователей получает нашу версию функции;
* другая — альтернативную;
* сравниваются заранее определённые метрики;
* дополнительно контролируется влияние предупреждений на пользовательский опыт.

Если полноценный A/B-тест невозможен, можно начать с ограниченного пилота на небольшой группе пользователей.

# Ретроспективный разбор

Первоначальное решение было ориентировано прежде всего на общую концепцию продукта, пользовательский сценарий и идею экспериментальной проверки.

При повторном разборе я бы значительно глубже проработал логику определения риска и систему метрик.

## Что было сделано хорошо

* Было предложено не вмешиваться в каждую операцию пользователя.
* Учитывался контекст поведения конкретного пользователя.
* Был рассмотрен конкретный пользовательский сценарий.
* Предупреждение не блокировало действие пользователя.
* Была предложена возможность объяснить пользователю причину предупреждения.
* Для сравнения альтернативных решений был предложен A/B-тест.

## Что я бы изменил сейчас

### 1. Разделил бы типы рисков

Мошеннические переводы и рискованные инвестиционные решения — разные задачи.

Для них могут использоваться разные признаки, модели риска и критерии успеха.

### 2. Глубже проработал бы систему метрик

Одной метрики снижения финансовых потерь недостаточно.

Я бы разделил метрики на:

**Основные:**

* снижение подтверждённых рискованных операций;
* снижение финансового ущерба.

**Поведенческие:**

* доля пользователей, изменивших действие после предупреждения;
* доля пользователей, открывших объяснение риска.

**Guardrail-метрики:**

* доля ложных предупреждений;
* влияние на конверсию нормальных операций;
* количество игнорируемых предупреждений.

### 3. Не делал бы вывод о риске только по отдельным признакам

Например, появление нового актива, большое количество покупок и отсутствие продаж сами по себе ещё не доказывают, что перед пользователем финансовая пирамида.

Такие признаки могут быть сигналами для дополнительной проверки, но не окончательным основанием для категоричного предупреждения.

### 4. Обосновал бы использование каждого источника данных

Для каждого признака стоит ответить на вопрос:

> Как именно эта информация помогает определить риск?

Это позволяет избежать сбора данных «на всякий случай» и делает архитектуру решения более обоснованной.

## Итог ретроспективы

Первоначально я в первую очередь концентрировался на концепции AI-функции, пользовательском сценарии и общей логике эксперимента.

При повторном разборе я бы больше внимания уделил формализации risk scoring, разделению типов рисков, системе основных и защитных метрик, контролю ложных срабатываний и более глубокой проверке альтернативных гипотез.

Этот кейс показывает не только первоначальное решение задачи, но и изменение моего подхода к продуктовой аналитике.
